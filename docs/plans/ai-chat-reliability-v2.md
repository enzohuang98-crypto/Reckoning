## 0. 一頁摘要

### 先講不舒服的真相
1. **「送出後沒有回覆」主要不是網路或 API 的單點 bug，而是產品契約本身。** 一鍵解說要求免費模型一次輸出約 2,000 tokens、格式完美的大 JSON（審查＋五段＋因果鏈＋K/E 編號＋≥400 漢字），再用數十條規則逐條檢查；**任何一條不過就整篇丟棄，不修補、不退回、不顯示**（`HarnessOrchestrator.ts:2076`、`:2722–2815`、`:3514–3526`）。[Certain]
2. **已有實證：** 暫停中的 PR #76（124 commits、約 1.7 萬行）真實免費模型測試 **沒有任何一次被接受的答案**。[Certain，PR #76 `docs/operations/paused-review-2026-10-11/`]
3. **繼續加驗證規則會讓情況更糟。** PR #76 為了檢查自然語言寫了 658 行的中文吃子/時序解析器，每題 5 次模型呼叫，仍然 0 個合格答案。這是「驗證器軍備競賽」，要停止。[Certain]
4. **免費模型的象棋推理能力本來就弱。** 讓模型自己從 FEN＋中文主線推「哪步吃了什麼、誰被將軍」必然出錯；品質上限取決於「程式先算好多少事實」。[Likely]

### 建議（已依使用者回答定案）
- 從 `main` 重來，只移植 PR #76 中可獨立驗證的小段（逐手重播事實、推理關閉政策、JSON 錯誤分類）。
- 新增 **v2 解說管線**：**程式算事實 → AI 用白話講解 → 驗證器只查客觀事實 → 有錯就自動叫模型修正一次 → 仍失敗就給「引擎重點摘要（非 AI）」＋清楚原因**；以旗標並行導入，v1 保留可回滾。
- 回答原則：**先直接回答問題、完整但不講廢話、初學者看得懂**；取消 400 漢字下限與湊字樣板。
- 免費模型故障時可用使用者核可的備援免費模型，**介面明示「本次由 X 回答」**。
- 驗證器發現客觀硬錯時，自動把「錯誤清單＋事實表＋上次回答」送回同一模型修正 **1 次**（每次重跑消耗免費額度並多 10–40 秒；第二次仍錯通常是模型能力問題）。

## 3. v2 解說流程

```
問題/提交 → 確定性捷徑（兵卒規則、輪到誰）── 命中 → 直接回答（不叫模型）
     ↓ 未命中
確保主線夠長（最多 1 次、≤5 秒引擎補算）
     ↓
ExplanationFacts（純函式）：逐手重播（誰走、哪個子、吃了什麼、是否將軍、走後威脅且有無保護）、
     主線結束子力、兩條線的關鍵差異、錯誤等級、將死/困斃偵測
     ↓
Prompt v2（system＋user、純文字、依模式：一鍵解說／局面／追問）
     ↓
模型呼叫（串流；推理依能力關閉或限額；單次 60 秒、總計 110 秒）
     ├ 429(分鐘)/5xx/403/404/逾時/空白 → 備援免費模型 1 次（明示）
     └ 每日額度用完/401/402 → 不備援，直接給清楚訊息
     ↓
AnswerCheck（只查客觀硬錯）
     ├ 無硬錯 → 交付 AI 回答
     └ 有硬錯 → 自動修正 1 次（附錯誤清單）→ 再查
                 ├ 通過 → 交付
                 └ 不通過 → 交付「引擎重點摘要（非 AI 生成）」＋原因＋重試按鈕
```

**預算**：每題最多 3 次模型呼叫（一般 1 次），單次 60 秒、總 110 秒、renderer 120 秒；串流閒置 30 秒中止。
**teacher-test 正式案例**（`interactionKind !== 'ordinary'`）仍走 v1，直到 P4-5 決定。

### 回答格式原則
- 第一句直接回答；每段 1–4 句；能少就少；不重述題目、不寫開場白、不湊字。
- 一鍵解說用小標題（結論／這步的問題或這步好在哪／首選想做什麼／對手怎麼利用／下次怎麼想）；差距很小或走對時不硬找缺點。
- 棋手寫了「原因」時，必須直接回應那個想法在主線中成不成立。
- 追問只答這一題，不重講整篇。
- 分數只說差距大小，不當理由；主線不說成「必然/唯一/被迫」。

## 4. 批判性檢驗（摘要）

**最可能失敗的三個原因**
1. 事實表不足以支撐「策略性為什麼」，模型補上錯誤戰略而客觀驗證抓不到 → **發布前需人工審 30 則**。
2. 免費模型池與額度波動；修正與備援都會消耗帳號層級的每日額度。
3. 低階模型執行風險（AnalysisPanel 狀態機與 IPC 細節易被改壞）。

**最有說服力的反方論點**：直接用便宜付費模型比工程化免費模型划算。它不改變 v2（v2 對所有 provider 都有益），但改變建議：把便宜付費模型列為「推薦」，免費模型標示「可用但不保證」。

**最可能推翻整個計畫的假設（A1）**：給了事實表，免費模型多數時候能寫出正確、有用的解說。由 P3-9 live 評分驗證。

**80/20**：最先刪 400 漢字下限與湊字樣板、一鍵大 JSON、對話用多輪引擎研究；必要核心是 D5/D6/D8/D12 修正、推理感知預算、v2 單次純文字呼叫＋事實表＋客觀驗證＋自動修正一次＋引擎摘要。若 P3-9 人工審核中 >20% 的 AI 答案有錯誤策略敘述 → 對付費模型恢復「結構化主張＋引用」模式。

## 5. 執行規則（每個任務都適用）

1. 一次只做一個任務；一個任務一個 commit（訊息：`P1-1: …`）；完成後跑該任務列出的測試。
2. **絕不**把 API key 寫進任何檔案、測試、log、commit、PR。live 腳本只讀環境變數 `OPENROUTER_API_KEY`，輸出時遮蔽。
3. **不得修改**：引擎分數視角與錯誤分級閾值（CLAUDE.md 原則 §4、§6）、IPC 來源驗證、SecretStore 加密、Base URL 安全規則、main 不可同步 I/O（§9）。
4. **不得刪除或放寬既有測試來讓它通過**。只有任務卡明確列出時才改寫測試，並在 commit 說明原因。
5. Phase 1–3 期間不得改動 v1 Harness 邏輯，除非任務卡明確指定該行。
6. UI 字串用繁體中文；錯誤訊息不得包含 provider 原文、金鑰或 prompt。
7. `src/shared/logic/**` 必須是純函式；renderer 不得 import main 或 `node:*`。
8. 新測試沿用現有風格（`node:assert/strict`、本機 HTTP mock server），並加入 `package.json` 的 `test` 指令鏈。
9. 遇到計畫沒涵蓋的情況：停止並回報。
10. 只能在 Windows CI 跑：`tests/security/security.test.ts`、`tests/unit/main/engineRegistry.test.ts`、`tests/e2e/engine.e2e.ts`、所有 `electron …` 測試。

## 7. 驗收標準

| 階段 | 成功標準 |
|---|---|
| P1 | D5–D8、D12、D13 消失；任何請求 ≤120 秒有結果或錯誤卡 |
| P2 | 空白/截斷比例下降（以 P0-2 前後比較） |
| P3 | **交付率 ≥95%**（AI 或摘要，110 秒內）；**AI 答案比例 ≥80%**；**每題呼叫中位數 1、上限 3**；**0 次外洩內部格式／不存在著法**；**人工評分 ≥4 分佔 ≥70%**；首字中位數 ≤15 秒、完成中位數 ≤45 秒（[Guessing] 目標） |
| P4 | 程式行數明顯下降、文件與現況一致 |
| P5 | Windows CI＋安裝版 10 步全部通過 |

**P3-9 demo 門檻（2026-10-16 起）：** 這個作品用於特殊選材 demo，使用者同意「適當降低、但不能太差」。
P3-9 改為：
- **demo 用模型**（目前 qwen/qwen3.8-flash，付費）：交付率 ≥95%、AI 答案比例 ≥80%、呼叫中位數 1／上限 3、0 外洩。
- **人工評分**：≥4 分佔 **≥60%**（原 70%），**且沒有任何一題 ≤2 分**（不能出現明顯講錯的回答）；固定調整題（`cases.json`）與保留驗證集（`holdout-cases.json`）**都要達標**，只過固定題不算。
- **免費模型**：只要求交付率 ≥95%（拿不到 AI 時交付標示清楚的引擎摘要）；AI 答案比例與品質不設門檻，受 OpenRouter 免費額度限流影響太大。

**回滾**：設 `XQA_EXPLAIN_PIPELINE=v1` 或還原單一 commit。
